## N4 / A05 — Saved Does Not Mean Loaded — 3 minutes

Saved convention changes from `Checklist` to `Supplies to confirm`.
The observed next heading still says `Checklist`. Keep four checks distinct:
Saved; Discovered/applicable/enabled; Included in this request/session;
Followed in the result. Discovered means found by the host, applicable means
the scope matches, enabled means not disabled, included means sent in this
request, followed means the result satisfies the instruction.
Included does not guarantee followed. Behavior alone does not prove which
file was included. Riley returns evidence; human Mergewell checks it.

Main displays CLI `/instructions` and `/env`, instruction refresh versus
skill reload, VS Code settings/`applyTo`/References/Diagnostics, and unverified
save-to-active-turn timing. CLI Details preserves task state first, then the
documented exit/resume `copilot --continue` or new session `/new`. Instruction
edits are not immediately available in active CLI sessions. This is not
`/skills reload` or proof of cache deletion. VS Code Details retains host and
version, file location, explicit matching `applyTo`, response References,
customization Diagnostics, experimental setting-dependent nested `AGENTS.md`,
and `/instructions` as configuration rather than CLI command semantics.
These are references, not a live reset demonstration.

Question: “The saved heading changed, but the response did not. What would you
check before concluding the model ignored the new rule?”
Recovery: “First check the host and version, discovery, scope and whether that
file is enabled. Then check which version reached this session. Only after
that do we check whether the result followed it. A heading appearing once
would show behavior, not prove where the rule came from.”
Transition: “Loaded instructions are one source of continuity. Selective
memory is a different mechanism, with its own limits.”
Sources: V C5/X6/X7/X9; P8/P13/P15/S7/S8.

## T7 / A10 — Reusable Skills — 3 minutes

Three conditional stages: discover metadata/description; when selected, use
the `SKILL.md` body; as needed, access resources. Metadata is a name and
description, not zero context. Discovery is not invocation. Do not depict
every installed procedure as active or loaded in a real request.

Example: reviewed supplies-check procedure identifies requirements, compares
a draft list, flags unknown quantities. Riley is the software collaborator,
the skill is the reusable procedure, the tool performs an action. A skill
does not establish an MCP connection or work independently. Review provenance,
dependencies, scripts and data access first. Optional forked context depends
on host/settings. Details preserves `/skills reload`, `/skills info NAME`,
availability/location rather than instruction-session refresh, an old body's
possible presence in history, and host/build testing for edited-skill
activation. Clue Wrangler remains a reviewed-procedure metaphor, not a
built-in feature, newly authored skill or new gadget.

Question: “If the host discovers the supplies-check skill, is the whole
procedure already active in every request?”
Recovery: “No. Discovery metadata helps it find a relevant skill. The selected
body and needed resources load when used. Check actual use rather than
assuming every installed procedure is in the request.”
Transition: “A skill captures a procedure. A custom agent captures a recurring
role and its boundaries.”
Sources: V C6, P9/P16/P10/P11; AGT-09.

| Mechanism | Independent event change | Full conditional effect |
| --- | --- | --- |
| Instructions | Saved output heading becomes Supplies to confirm | Changes supplied guidance only when applicable, enabled and loaded. |
| Skill | A reviewed supplies-check procedure is added | Discovery metadata can change; selected body/resources load when used, not merely because the folder exists. |

schemas, order, deferred discovery and profile support vary by host.
MCP here means a connection to an approved capability, not a setup lesson.
